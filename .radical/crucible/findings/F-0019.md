## Steps

1. POST /events {id: {"order":"X","type":"order.paid"}, type:'order.paid', orderId:'X'}  → 200, recorded
2. POST the same body again  → 200, recorded again
3. GET /notifications?orderId=X lists 2 notifications with the same text

## What differs

```text
Expected: One notification for X: the second POST is answered with the first notification, or refused with a 4xx because the id is not a string
Actual: Two notifications for X, each with eventId {"order":"run3-obj-…","type":"order.paid"} and text "Your payment arrived."; both POSTs answered 200 (2 of 2 runs, the string-id control gave 1 notification)
Seen: 2 of 2
Where it probably comes from: services/notifications/src/notifier.ts handle(): the Map is keyed on event.id, and a JSON object is a new key each time, so the lookup never matches (guess: no id type check in services/notifications/src/server.ts, as with F-0012)
A test that would catch it: services/notifications: an event whose id is not a string is refused with a 4xx; and a repeat of an event id (also an object id sent twice) is recorded once
```
